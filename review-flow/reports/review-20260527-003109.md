## Findings

### F-01 [P1] [requirements] Capture Current Scene cannot read bulbs missing from the discovered device map

- Finding ID: `F-01`
- Affected scope: Animated Scene scene capture workflow
- Package: N/A
- File: `streamdeck/streamdeck.go:352`
- Reviewer: Domain and Business Logic Auditor, Architectural Lead, Reliability and Quality Engineer
- Evidence: `sendSceneColorsToPropertyInspector` reads `c.controller.GetDevices()`, optionally calls `DiscoverDevices()` once, then calls `GetCurrentColor(devices[mac])` for every requested MAC. If discovery still does not populate the device, the value passed is `nil`; `lifx.GetCurrentColor` returns `cannot get color for missing device` at `lifx/lifx.go:187`. Scene playback does better: `resolveDevices` falls back to `deviceFromMac` broadcast when a selected MAC is missing from the device map at `lifx/lifx.go:375`.
- Risk: This contradicts the main requirement for copying the current scene from selected bulbs. A bulb can be controlled by Animated Scene through MAC-only broadcast fallback, but the new capture button cannot read it if discovery/cache misses it. That is especially likely for the same network conditions this branch already worked around.
- Fix direction: Add a controller-level capture API, for example `GetCurrentColors([]models.Device)`, that reuses `resolveDevices` or a shared MAC resolver before reading colors. Keep `streamdeck.Client` responsible for translating PI messages, not reimplementing LIFX resolution policy. Add a regression test for a selected MAC absent from `GetDevices()` but resolvable through fallback.

### F-02 [P1] [error-handling] Partial scene capture preserves stale per-device colors for failed bulbs

- Finding ID: `F-02`
- Affected scope: Animated Scene partial capture behavior
- Package: N/A
- File: `property-inspector/set-scene-pi.html:375`
- Reviewer: Reliability and Quality Engineer, Domain and Business Logic Auditor
- Evidence: The backend returns partial `colors` plus `errors` and only sends a hard failure when no colors were captured. The PI updates only the MACs present in `colors`, logs `data["errors"]` to the console, and then saves settings. Existing `deviceColors` entries for failed MACs remain intact. Runtime prefers per-device entries over the fallback color at `lifx/scene.go:318`.
- Risk: If a bulb had an older captured color and a later capture fails for that bulb while others succeed, the saved scene becomes a mix of fresh targets and stale targets. The UI gives no visible warning, so the next animation can drive that failed bulb to an old color instead of the current scene or fallback.
- Fix direction: Make partial capture explicit. Either fail the whole capture without saving any new per-device colors, or remove failed selected MACs from `deviceColors` so they fall back to the shared color. Surface failed device names in the PI instead of only logging to the console, and add a regression test for partial success with pre-existing per-device colors.

### F-03 [P2] [input-validation] Bulk scene-color capture accepts unbounded, unvalidated MAC payloads

- Finding ID: `F-03`
- Affected scope: Property Inspector `getSceneColors` message handling
- Package: N/A
- File: `streamdeck/streamdeck.go:119`
- Reviewer: Security Sentinel, Performance and Resource Specialist
- Evidence: The `getSceneColors` branch accepts `msg.Payload["macs"]` after only converting values to strings and checking that the list is non-empty. `payloadStringSlice` does not validate MAC format, dedupe entries, cap count, or cap string length. The full list is then processed synchronously, with raw MAC strings used in logs and in the response `errors` map.
- Risk: A malformed local PI/websocket payload can trigger many sequential network reads, log oversized or forged-looking identifiers, and produce large response payloads. Even benign stale settings can cause long waterfalls because every requested MAC is read one at a time.
- Fix direction: Validate server-side before capture: require canonical MAC format, drop duplicates, cap to `maxSceneDevices` or an exported equivalent, reject/truncate overlong strings, and avoid logging raw invalid identifiers. Consider bounded concurrency and a per-capture deadline so backend work cannot run long after the PI timeout.

### F-04 [P2] [state-management] Capture Current Scene silently rewrites the fallback color from an arbitrary captured bulb

- Finding ID: `F-04`
- Affected scope: Animated Scene settings model and Property Inspector capture behavior
- Package: N/A
- File: `property-inspector/set-scene-pi.html:379`
- Reviewer: Architectural Lead, Clarity and Style Enforcer
- Evidence: `sceneColorsReceived` takes `Object.keys(colors)[0]` and writes that bulb's captured color into `actionInfo.payload.settings["color"]`. Runtime uses `deviceColors` first and falls back to `TargetColor` when no per-device color exists. The backend builds `colors` as a Go map, so the first key is not a stable user-selected bulb.
- Risk: Capture has a hidden side effect on the shared fallback target. On partial capture or later-added devices, an uncaptured bulb may animate to a surprising captured color, and the chosen fallback source can be nondeterministic.
- Fix direction: Do not mutate `settings["color"]` during scene capture. If fallback update is desired, make it explicit and deterministic, such as a separate command that copies the currently selected "Settings to copy" bulb into the fallback target.

### F-05 [P2] [network] Scene capture performs sequential network reads without a backend deadline

- Finding ID: `F-05`
- Affected scope: Property Inspector scene color capture
- Package: N/A
- File: `streamdeck/streamdeck.go:365`
- Reviewer: Performance and Resource Specialist
- Evidence: `sendSceneColorsToPropertyInspector` loops through requested MACs synchronously and calls `GetCurrentColor` one device at a time. The PI resets its button after 12 seconds, but that timeout does not cancel backend capture work.
- Risk: Slow or unreachable bulbs multiply capture latency. If Stream Deck dispatches plugin messages serially, this can delay unrelated PI/plugin messages while color reads continue after the UI has given up.
- Fix direction: After validation/deduping, run color reads with bounded concurrency and a backend deadline aligned with the PI timeout. Return partial results with explicit failures when the deadline expires.
