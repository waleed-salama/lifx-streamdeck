## Findings

### F-01 [P2] [correctness] Captured-off devices do not restore their captured color state

- Finding ID: `F-01`
- Affected scope: Animated Scene activation for captured target-off devices
- Package: N/A
- File: `lifx/scene.go:95`
- Reviewer: Domain and Business Logic Auditor, Reliability and Quality Engineer
- Evidence: When `target.PowerOn` is false, `buildSceneCommands` appends only a power-off command at `lifx/scene.go:95-98` and immediately continues. The captured `target.Color` is never sent for that device, even though captured off bulbs store and display H/S/B/K values.
- Risk: A scene can leave the bulb powered off correctly while its hidden color remains whatever it had before. The next manual power-on or current-state transition can reveal the wrong color, which weakens the captured per-device scene contract.
- Fix direction: After the power-off transition completes, schedule a zero-transition color command using the captured target color, similar to the reverse-scene restore path. Use an ordering such as `delay + transition + sceneOffRestoreDelay` so an on bulb does not visibly flash the hidden target color before powering down.

### F-02 [P2] [network] Scene capture does a second power read that adds latency and can discard valid color captures

- Finding ID: `F-02`
- Affected scope: Capture Current Scene
- Package: N/A
- File: `streamdeck/streamdeck.go:367`
- Reviewer: Domain and Business Logic Auditor, Performance and Resource Specialist
- Evidence: `sendSceneColorsToPropertyInspector` calls `GetCurrentColor` at `streamdeck/streamdeck.go:367`, then calls `GetPowerState` at `streamdeck/streamdeck.go:373`. If the second call fails, the code records an error and continues before adding the already captured color to `colors`. `golifx.Device.GetColorState()` already returns `DeviceState.Power` along with `DeviceState.Color`, so the extra request is avoidable.
- Risk: Capture now performs up to two sequential LAN reads per selected bulb, which can slow large scenes and increase UDP timeout risk. It also creates a partial-failure mode where color was captured successfully but the PI keeps stale saved data because power lookup failed.
- Fix direction: Add or use a controller method that returns full scene state from one `GetColorState` call, including color and power, while keeping the current direct/broadcast fallback behavior. If a partial failure still exists after that refactor, preserve successfully captured color and avoid overwriting unknown power state.
